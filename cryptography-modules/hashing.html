🧩 What is hashing?

A cryptographic hash function transforms an input of arbitrary length into a fixed-length output called a digest. SHA-256 always produces 256 bits (64 hexadecimal characters), whether the input is one letter or an entire file.

Hashing ≠ Encryption

Encryption uses a key to enable authorized reversal. Cryptographic hashing has no decryption key; its output is designed not to reveal the original input.

Hashing ≠ Encoding

Encoding, such as Base64, is reversible and does not provide secrecy or cryptographic integrity.

CONCEPT STATION · 5 XP

🛡️ Essential properties of cryptographic hash functions

A cryptographic hash maps an input of any length to a fixed-length digest. These properties describe what a secure hash should do—and what an attacker should find difficult.

📏 Fixed-length output

SHA-256 produces 256 bits (64 hexadecimal characters) whether the input is a sentence or a large file.

⚡ Efficient computation

Given a message, computing its hash is fast and repeatable. Identical input bytes always give the same digest.

↛ First-preimage resistance

Given only a target digest h, it should be infeasible to find any message m such that H(m)=h.

🛡 Second-preimage resistance

Given a specific message m, it should be infeasible to find a different message with the same digest.

🔀 Collision resistance

It should be infeasible to find any pair of different messages with the same digest, even when an attacker chooses both.

🌊 Avalanche effect

A tiny input change typically changes about half the output bits. Try the interactive SHA-256 comparison below.

Remember: Hashing is not encryption. Collisions must exist mathematically for a fixed-length digest, but secure hash algorithms make useful collisions extremely difficult to find. For password storage, use a dedicated password KDF rather than SHA-256 alone.

PRACTICAL APPLICATIONS

🌍 Where hashing protects systems

📦 File integrity

Compare trusted SHA-256 digests to detect accidental or malicious changes to downloads. A digest alone is not proof of authenticity unless the reference is trusted.

✍️ Digital signatures

Signature algorithms commonly sign a digest of a message; collision resistance helps prevent substitution attacks.

🔐 Password verification

Store a per-user salt and a slow, memory-hard password-derived value rather than plaintext passwords or fast SHA-256 alone.

🔗 Data structures

Merkle trees combine hashes to verify collections of records efficiently; blockchain designs also use hashes.

🧾 Deduplication

Hashes help identify likely duplicate files, but security-critical workflows may need additional verification.

🧪 Forensic workflows

Analysts record hashes to help verify evidence integrity during handling and analysis.

CHALLENGE 4 · 10 XP

🔒 Password storage: Choose the defense

Hashing passwords is not the same as encrypting them. A stolen database can still enable offline guessing. Fast general-purpose hashes (MD5, SHA-1, SHA-256) are unsuitable on their own for password storage.

❌ Weak design
stored = SHA256(password)

Fast to guess; identical passwords produce identical digests without unique salts.

✅ Stronger design
salt = random_per_user()
stored = Argon2id(password, salt, cost)

Unique salts defeat reusable precomputed tables; an appropriately configured password KDF makes guesses more costly.

PASSWORD SECURITY · DEFENSIVE DEEP DIVE

🛡️ Argon2id: Protecting stored passwords

Argon2id is a modern, memory-hard password hashing algorithm designed to make offline password guessing costly. Unlike a fast general-purpose hash such as SHA-256, it deliberately consumes time and memory. It combines data-independent and data-dependent memory access patterns.

🧂 Unique salt

Each account gets its own randomly generated salt. Even when two people use the same password, their stored password verifiers differ.

🧠 Memory cost

Memory use makes massively parallel guessing more expensive for attackers.

⏱️ Time cost

More computation per guess slows bulk offline attacks. Choose parameters by measuring your server's capacity.

🌈 Rainbow tables and breached password databases

Real breaches have exposed password hashes. Attackers may test common passwords against unsalted fast hashes, or use precomputed rainbow chains to reduce repeated work. A simple hash-to-password dictionary is not technically a rainbow table; the lookup below makes the core reuse risk easy to see before introducing chains.

Realistic breach scenarios

Unsalted legacy hashes

A breach exposes many fast unsalted digests. The attacker can reuse one precomputed candidate set across the whole database.

Same password, many users

Two accounts sharing a password also share an unsalted digest; identical values reveal password reuse.

Modern password storage

Unique salts + Argon2id break reusable tables and increase per-guess cost. Weak passwords still need protection.

2008 · Certificate trust

MD5 rogue CA certificate

Researchers exploited practical MD5 chosen-prefix collisions to demonstrate a forged intermediate certificate authority in a controlled research setting, highlighting why weak hash functions endanger digital signatures.

2017 · SHA-1

SHAttered collision

Researchers published two different PDF files with the same SHA-1 digest, demonstrating a practical collision and accelerating migration away from SHA-1.
